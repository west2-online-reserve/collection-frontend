## 1. 为什么我决定认真学前端

2026-10-21 ｜ 随笔

我学前端的方式，一开始是错的。

大二上参加过两个比赛，项目都是我用 AI 搭的。我能说清楚要什么页面、什么配色、什么交互，AI 负责写代码。交付时项目能跑，答辩也过了，但心里清楚：那些代码我一行都写不出来。

最典型的一次，我想把标题字号从 24px 改成 28px。打开 VS Code，找到那行，然后去问了 AI「怎么改字号」。

### 问题不在会不会，在有没有

后来我想明白了：我不是「不会写」，是「没有写过」。这两件事看起来差不多，实际差得很远。

会写的人遇到没见过的需求，能拆解、能查文档、能试错。没写过的人只会描述需求，然后等人给答案。前一种能力可以迁移到任何技术栈，后一种换个框架就归零。

而且我有个更麻烦的毛病：看 AI 写的代码，觉得「懂了」，但关掉对话框就写不出来。这是一种很舒服的错觉，因为它不需要付出任何代价——直到你真的要独立做一个东西。

### 我决定怎么改

三条：

- 关掉所有 AI 代码补全。让它只回答问题，不写代码
- 不追求「学完再做」，直接拿一个真项目边做边学
- 每天至少一个 commit，记录当天做了什么、卡在哪

这个博客就是那个项目。首页、文章页、关于页，从空白文件开始，一行行敲。

写第一篇文章的时候我还不确定能不能坚持。现在回头看，从搭骨架到能切换深色模式，用了十天。慢，但每一步都是自己的。

## 2. 盒模型：为什么我的元素比写的宽

2026-10-22 ｜ CSS

学 CSS 第一个把我绊住的不是布局，是一个特别简单的问题：我写 `width: 200px`，为什么元素占了 244px？

### 先看算式

我给一个盒子写了三样东西：

- `width: 200px`
- `padding: 20px`
- `border: 2px solid`

我以为它宽 200。实际占 244。

因为浏览器默认的 `box-sizing` 是 `content-box`——`width` 只算内容区，`padding` 和 `border` 加在外面。

算一遍：200 + 20×2（左右各 20）+ 2×2（左右各 2）= 244。

这里我犯过一个错：把 `padding: 20px` 理解成「总共 20」。它其实是「每边各 20」，左右加起来 40。CSS 里所有间距类的值都是每边的，算总宽高时左右要 ×2。

### border-box 解决什么

改成 `border-box`，`width` 就包含 padding 和 border，写 200 就真的是 200，内容区被自动压成 156。

几乎所有项目都会全局设一次：`*, *::before, *::after { box-sizing: border-box; }`

理由很实际：如果你写 `width: 100%` 再加 padding，用默认值元素会溢出容器，页面右边多出一条横向滚动条。这个「莫名其妙多了条滚动条」的坑，十次有九次是盒模型。

### 它什么时候救了我

写 `main { max-width: 900px; padding: 0 24px }` 的时候。因为设了 border-box，元素实际还是 900 宽，内容区被压到 852。如果没设，它就是 948 宽，在 900 的容器里直接溢出。

那条全局规则写在文件第一行的时候，看起来像仪式。真正干活是在两周后。

## 3. Flex 排一条线，Grid 排一个面

2026-10-23 ｜ CSS

这两个我一开始总混。后来用一句话分清了：Flex 排一条线，Grid 排一个面。

### Flex：一行里的东西怎么排

导航栏是典型场景。站名在左，三个链接在右，垂直居中。给 header 设 `display: flex`，再配三个属性就够了：

- `justify-content: space-between` 两端顶开
- `align-items: center` 垂直居中
- `gap` 孩子之间的间距

有个地方我理解错了很久：flex 只作用于直接子元素，不会往下传染。

我给 `.site-header` 设了 flex，导航的 `li` 也横排了——但这不是 header 的功劳，是因为我同时给 `ul` 也设了 flex。两层 flex，各管一层。把 `ul` 那条删掉，`li` 立刻变回竖排带小圆点。

### Grid：行和列一起管

文章列表用 Grid。一行代码定义三列：`grid-template-columns: repeat(3, 1fr);`

`1fr` 是「份数」，不是长度单位。浏览器拿到容器宽度，先减掉 gap，再按份数分。容器 900、gap 48，三列各 284——这个数字是算出来的，不是我写的。

所以 `1fr` 会跟着容器伸缩，写死 `300px` 就不会。三列各 300 是 900，浏览器窗口 800 的时候装不下，直接溢出。这就是为什么布局里能相对就别写死。

### 什么时候用哪个

- 导航栏、工具栏、按钮组 → Flex
- 卡片列表、相册、仪表盘 → Grid
- 拿不准 → 想想「我是在排一行，还是在排一片」

## 4. 响应式不是三个版本，是一套代码

2026-10-24 ｜ CSS、随笔

我一开始以为响应式是「做手机版、平板版、桌面版三个页面」。不是。是一套代码，在不同宽度下自动变。

### 断点不是随便定的

768px 和 1024px 这两个数字，是 iPad 竖屏和横屏的视口宽度。不是设计师拍脑袋，是设备宽度。

我的卡片列表三档：小于 768 一列，768 到 1024 两列，大于 1024 三列。

### 移动优先是什么意思

先写手机的样式，再用媒体查询往大屏加。

基础规则写 `grid-template-columns: 1fr`（一列，手机），然后加两个媒体查询：768px 以上两列，1024px 以上三列。

只有两个断点，覆盖三档。因为条件会叠加：宽度 1200 的时候，基础规则、768 那条、1024 那条全部生效，最后一条赢。

反过来做（桌面优先，用 `max-width` 往下减）也能实现，但会写出一堆覆盖规则，越写越乱。

### 一个我踩过的坑

媒体查询是「覆盖」，不是「重新定义」。

我在手机样式里写了 `flex-direction: column`（导航竖排）。到了桌面，如果媒体查询里不写 `flex-direction: row`，`column` 会继续生效——桌面导航还是竖的。

所以规律是：手机样式里设过、桌面上不想要的属性，都必须在媒体查询里再写一遍改回来。

还有一条：媒体查询必须写在文件末尾。因为里面的选择器和外面特异性相同，靠顺序决定胜负。写在前面会被后面的基础规则盖掉，而且不报错，你只会觉得「媒体查询没生效」。

### 怎么验证

F12 打开开发者工具，按 Ctrl+Shift+M 开设备模拟，或者直接拖窗口。三个宽度各看一遍，重点看两件事：列数对不对，有没有横向滚动条。

有横向滚动条就是失败。说明某个元素超出了视口，九成是写死了宽度或者漏了 border-box。

## 5. 我的第一个 Git commit

2026-10-25 ｜ 工程

之前我以为 `git commit` 就是「上传到 GitHub」。不是。

### 三件事，三个层次

- `git init`：在这个文件夹建一个仓库，纯本地，不联网
- `git add` 加 `git commit`：把当前状态存档在你自己硬盘上，不联网，不需要账号
- `git push`：把存档传到 GitHub，要联网要账号

前两步跟 GitHub 一点关系都没有。我拖了四天才做第一个 commit，理由是「内容太少，等做完了再传」。这个理由对 push 成立，对 commit 完全不成立。

### commit 是给自己的时间机器

第二天开始写 CSS，我反复改那三个文件。改到某一版发现导航崩了，想退回去看看昨天长什么样——

- 有 commit：`git diff` 一眼看出改了什么，`git checkout` 秒回退
- 没 commit：只能凭记忆重写

而且它不会出现在你的 GitHub 主页上，没人看得到。它只对一个人有用：三个月后想搞清楚「这个功能是什么时候加坏的」的你。

### commit 信息怎么写

我一开始写 `update`、`fix`。后来发现这些词等于没写——三个月后看 `update`，完全不知道那天干了什么。

现在写的是当天做了什么：

- 项目一 D1：三页骨架加需求清单
- 项目一 D3：Grid 卡片列表、详情页排版、三档响应式
- 项目一 D5：详情页按 id 渲染、localStorage、深色模式

一句话说清「这次改了什么」，不用点进去看代码就知道。

## 6. 下一站：用 JS 把数据变成页面

2026-10-26 ｜ JS

写到这里的时候，我的首页还是三张手写的卡片。加一篇文章要改 HTML，改三处地方。

现在的做法是：数据放数组，JS 生成页面。

### 数据长什么样

一个对象数组，每个对象是一篇文章：

- `id`：唯一编号，详情页靠它找文章
- `title`、`date`、`summary`：显示用
- `tags`：又是一个数组，一篇文章可以有多个标签

这种「对象数组」是前端最常见的数据结构。以后从接口拿到的数据，基本都长这样。

### 三步把数据变成 HTML

- `map`：遍历数组，每一项转成一段 HTML 字符串，得到一个新数组
- `join("")`：把数组拼成一个字符串。不加会看到卡片之间多出逗号
- `innerHTML`：把字符串塞进容器，浏览器解析成真实节点

`map` 和 `filter` 我一开始总分不清。区别是：`map` 每项都处理，数量不变；`filter` 只留返回 true 的，数量会变。

### 筛选是重新渲染，不是藏起来

点标签筛选的时候，我没有去操作已有的 DOM，而是：拿到筛过的数据，清空容器，重新生成。

因为维护「DOM 和数据一一对应」太麻烦。而 `innerHTML =` 是替换，每次都是清空重画，数据和页面永远一致。

这个思路的正式说法是：数据是唯一的真相，页面是数据的投影。

后来我才知道，React 整个设计就建立在这上面——你只改数据，它负责把页面更新成数据的样子。所以现在这个土办法，其实是它的雏形。
